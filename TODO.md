# Vayal — Role-Based Prototype Outcomes

## Public discovery and onboarding
- [x] **Public Vayal landing page.** Create a public-facing landing page that explains the VAYAL platform. Include VAYAL branding and navigation; a hero section explaining the platform; a clear explanation of how VAYAL works; separate introductions for Farm Holders and Machinery Owners; benefits of renting agricultural machinery; benefits of listing machinery; how verification and booking work; a trust and safety section; frequently asked questions; and a footer with contact and platform information. The primary CTA is **Get Started** and it navigates to role selection.
- [x] **Role selection.** Create a dedicated role-selection page with two prominent cards. Farm Holder description: “Find and rent agricultural machinery near your farmland.” CTA: “Continue as Farm Holder.” Machinery Owner description: “Register your agricultural machinery and receive rental requests.” CTA: “Continue as Machinery Owner.” Each CTA enters the matching role's separate registration/login experience.
- [x] **Role-specific simulated mobile authentication.** For Farm Holder and Machinery Owner, provide mobile number entry, request OTP, six-digit OTP entry, verification, profile completion for first-time registration, and navigation to the corresponding dashboard. The OTP must be a clearly identified demonstration code, must not send SMS, and must not pretend that real mobile verification occurred. Persist prototype profiles/session locally where appropriate.

## Farm Holder experience
- [x] **Farm Holder dashboard and machinery discovery.** After simulated authentication, provide a dedicated dashboard with a welcome section, machinery search, location-based discovery UI, available machinery cards, machine photos, owner information, rental pricing, machine availability, operating area, and machine verification status. Search by machine name or category and by entered village, town, district or PIN code. Support categories: Tractors, Harvesters, Rotavators, Cultivators, Seed Drills, Ploughs, Sprayers and Other agricultural equipment. Include filters for price, distance, availability and machine type. Clearly label mock distance/location estimates as approximate prototype data; a manually entered location is not GPS verification.
- [x] **Machine details and booking.** A machine detail page shows photographs, machine name/category, owner details, specifications, rental price, operating location, availability calendar, operator availability, rental conditions and verification information; include a Book Machine CTA. Farmers can select required date, preferred time, number of hours or days, farm location and additional instructions. Show a booking summary before submission. Local booking statuses include Pending, Accepted, Rejected, Confirmed, Completed and Cancelled. Provide a My Bookings page to track requests. All booking changes are browser-local demonstration state only; they do not create a real rental arrangement.
- [x] **On-site OTP/location demonstration.** When the machine reaches the farmer's location, visually demonstrate that the operator must verify the booking before rental starts: operator reaches registered location; farmer confirms presence; farmer provides booking OTP; operator enters OTP; demo verifies it; status changes to On-Site Verified; rental can begin. Include location confirmation and show that farmer/operator are expected at the registered location. Keep this prepared for future GPS/geofencing integration, but never treat manually entered address or clicked confirmation as verified physical presence.

## Machinery Owner experience
- [x] **Owner dashboard and navigation.** After simulated authentication, provide a separate machinery-owner dashboard with total registered machines, available machines, active bookings, pending requests, illustrative earnings, verification status and recent booking activity. Role navigation must include Dashboard, My Machinery, Add Machinery, Booking Requests, Verification, Earnings, Profile and Logout.
- [x] **Six-step machine registration.** Build a multi-step interface with: Step 1 Basic Information—machine name, category, manufacturer, model, manufacturing year, identification/serial number; Step 2 Machine Details—horsepower/capacity, specifications, condition, applicable fuel type and description; Step 3 Photographs—front, side, rear and additional photographs; Step 4 Document Verification—uploads for ownership proof/purchase invoice, registration certificate where applicable, Fitness Certificate where applicable, insurance where applicable and other relevant documents; Step 5 Rental Information—hourly and daily rental prices, operator availability, operating locations, availability schedule and delivery/transport charges; Step 6 Review and Submit—show all entered information and allow submission for simulated verification. Do not require vehicle-specific documents universally; requirements depend on machine category and applicable regulations. Keep uploaded content local to the prototype and clearly disclose that it is not sent for real review.
- [x] **Verification details and statuses.** Show verification states Not Submitted, Submitted, Under Review, Verified, Rejected and Additional Documents Required. Provide a details page with review state and rejection reasons. The review mechanism is simulated, must be labelled as demo-only and must not imply a real authority reviewed the equipment. Only listings in the simulated Verified state may appear as verified to Farm Holders.
- [x] **Machine management and booking requests.** Owners can view registered machines, edit machine information, update rental prices, update availability, temporarily disable listings, view booking requests, accept/reject booking requests and view completed rentals. Provide a dedicated requests page. Each booking displays farmer details, machine, farm location, requested date/time, rental duration, estimated rental amount and status. Provide Accept and Reject actions. After acceptance, show confirmation and the on-site OTP process. Changes persist only in browser-local prototype state; no payment, SMS or live booking API is used.
- [x] **Illustrative earnings.** Add an earnings page/dashboard section with plainly illustrative, non-withdrawable demo totals and activity. Do not connect payment gateway, wallet, or payout service.

## Shared prototype behavior, visual system and boundaries
- [x] **Working responsive navigation and interactions.** Every major navigation element, button, form and interaction works through the frontend prototype, from public landing through Farm Holder and Machinery Owner journeys. Include Help Center, Profile and Logout in appropriate role navigation; retain practical responsive behavior and clear success, error, empty and progress states.
- [x] **Realistic, separated local mock data.** Use realistic mock farm holders, machinery owners, machine listings, machine availability, booking requests, verification records and rental pricing. Persist prototype data locally where appropriate. Keep all mock data and frontend state separate from future backend integration; do not call existing production-style APIs for prototype actions.
- [x] **Apply the Base-UI reference.** Use `Base-UI.zip` as the authoritative visual reference; read its `SKILL.md`, `DESIGN.md`, `VISUAL_GUIDE.md`, `COMPONENTS.md`, `LAYOUT.md`, `INTERACTIONS.md` and `ANIMATIONS.md`. Preserve existing VAYAL visual identity, Inter typography, warm agricultural color palette, spacing system, card/button styling, responsive layout and design quality while redesigning information architecture and individual screens for the new product experience.
- [x] **Frontend-only restrictions.** Build and run inside Manus Preview/local development only. Do not deploy to production, connect a real payment gateway, integrate an actual SMS provider, build a production database/backend, or treat prototype OTP, documents, location or bookings as real. Ensure the full prototype is navigable without a paid or external service.
